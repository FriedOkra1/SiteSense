1. Overview
-----------
- SiteSense is a browser extension that evaluates the privacy posture of any visited website and the installed extensions on the local browser profile.
- The production architecture pairs local extraction and guardrail logic with a Vercel-hosted privacy analysis API backed by Claude. Only sanitized policy excerpts leave the device; no user identifiers, browsing history, or telemetry are transmitted.
- Results are rendered in the popup UI and logged in an in-memory transparency ledger so every inference is auditable and exportable.

2. End-to-End Flow
------------------
1. **Detection & Extraction (Client, content script)**
   - The content script listens for navigation events. When a page loads, it inspects the DOM for policy-like text (length threshold with keywords such as “privacy,” “collection,” “retention,” etc.).
   - Extracted text is normalized locally (whitespace cleanup, boilerplate trimming) and truncated to the maximum payload size the backend accepts.
2. **Session Bootstrapping (Client, background service worker)**
   - The content script sends a `policy:scan` message to the background worker.
   - The background worker allocates a new `TransparencySession` keyed by `<url>::timestamp`, immediately logs a “processing” status message back to the UI, and queues the sanitized excerpt for outbound analysis.
3. **Guardrail Pipeline (Client preflight)**
   - Before any API call, the extension runs the excerpt through lexical filters, jailbreak classifiers, and high-risk keyword detectors (financial, medical, biometric vocab).
   - Segments that fail checks are redacted or rewritten in-place; if the prompt remains non-compliant, the request is blocked and the UI shows a clear failure message with links to the transparency log.
4. **Outbound Request (Client → Vercel API)**
   - The background worker constructs the structured prompt defined in `shared/prompts/privacy.ts`, including the JSON schema describing expected fields.
   - The sanitized excerpt, schema, and site metadata are POSTed over HTTPS to the Vercel API, authenticated with an environment-backed Claude API key that never ships with the extension.
5. **Claude Evaluation (Server)**
   - The Vercel server forwards the request to Claude with SiteSense’s system prompt and the JSON schema. Claude analyzes the policy against governance checklists and returns a structured payload (summary, normalized score, positives, risks, detailed rationales, citations).
6. **Post-Processing (Server)**
   - The Vercel handler validates the JSON response against the schema, applies calibration rules (e.g., bounding scores to 0.55–0.95 for MVP, smoothing drift against historical baselines), and stamps metadata (response time, model version, calibration bucket).
   - If validation fails, the server retries with fallback instructions; repeated failures return a descriptive error and incident code to the extension while logging the event server-side.
7. **Result Delivery (Server → Client)**
   - The validated payload plus calibration metadata are returned to the extension.
   - The background worker logs the response, updates the transparency session, runs the extension-permission audit (see Section 7), and broadcasts a `policy:scan-result` message to the popup/options UIs.
8. **User Presentation (Client UI)**
   - The popup renders the score, summary, strengths, risks, rationales, citations, and a “How this score was generated” transparency view that mirrors the transparency ledger entry.
   - The options page keeps the latest snapshot, offers filters, and exposes a one-click JSON export of all transparency sessions.

3. API Integration
------------------
- **Endpoint:** A Vercel serverless function (Edge-ready) that authenticates requests with API keys stored in environment variables (`CLAUDE_API_KEY`).
- **Request Payload:** An object containing the sanitized excerpt, target URL, and the prompt structure defined in `buildPrivacyPrompt` (`shared/prompts/privacy.ts`). The payload enforces `text.format = json_schema` to compel Claude to follow the schema.
- **Response Contract:** The server expects Claude to return `summary`, `score` (floats 0–1), `positives`, `risks`, `score_explanation`, `positive_details`, `risk_details`, and `citations`. Additional metadata (model latency, guardrail status, calibration tier) is appended server-side before the result is relayed to the extension.
- **Error Handling:** Guardrail breaches, schema mismatches, or Claude-side failures surface structured error objects with an incident code. The extension logs these as `error` events and informs the user to check the transparency export.

4. Scoring & Calibration
------------------------
- Claude returns a normalized privacy score between 0 and 1; the server maps it to a percentile-like band (e.g., 55–95) to maintain realistic spread in the MVP.
- Calibration references historical site baselines and enforces deterministic rounding so repeated scans of the same policy produce identical scores unless Claude’s rationale materially differs.
- The client UI maps the score to visual states (color, badge) and attaches the Claude-provided `score_explanation` to clarify the rating logic.

5. Guardrails & Audit Controls
------------------------------
- **Prompt Sanitization:** Multi-stage filters eliminate disallowed vocabulary, detect jailbreak instructions, and rewrite ambiguous phrasing before the request leaves the device.
- **Inference Validation:** The server validates Claude’s JSON against the schema, ensuring every field is present and typed correctly. Failed validations trigger retries with stricter instructions; persistent issues log an incident and block the response.
- **Honeypots & Decoys:** The extension and landing site expose hidden endpoints/prompts that legitimate users never touch. Hits indicate malicious probing; telemetry (hashed origin, timestamps, payload fingerprint) is captured, throttling the offender and notifying operators.
- **Rate Limiting & Anomaly Detection:** The backend enforces per-origin quotas and monitors unusual patterns (e.g., many unique URLs per minute) to mitigate automated attacks.
- **Recovery Paths:** Feature flags allow operators to pause outbound analysis, switch to maintenance messaging, or roll back to a safe configuration without losing the transparency ledger.

6. Transparency & Exportability
-------------------------------
- Every session generates a deterministic `sessionId` (`<url>::timestamp`) and a `TransparencySession` object that logs the sanitized prompt, analysis payload, extension audit, and response metadata.
- The popup’s transparency view and the options page allow users to inspect each event chronologically.
- Users can export the transparency ledger as JSON (`transparency:export` message) for audits, compliance reporting, or incident review.
- Exported data includes the sanitized prompt, Claude output, score, rationales, citations, guardrail notes, and any errors encountered.

7. Extension Permission Audit
-----------------------------
- Parallel to policy analysis, the background worker enumerates other installed extensions (excluding SiteSense itself) via the WebExtension Management API.
- Permissions are evaluated with deterministic rules defined in `shared/rules/permissions.ts`, assigning severity, rationale, and a normalized risk score.
- Audit results are logged into the same transparency session and surfaced beside the privacy score so teams can assess local extension risk alongside site posture.

8. Failure Handling & Recovery
------------------------------
- If the API call fails (network issues, guardrail blocks, schema errors), the background worker logs an `error` event, notifies the UI, and preserves the failed state in the transparency ledger.
- Users see actionable guidance (e.g., “Claude analysis failed. Check transparency log for details.”) and can export the log for debugging.
- Server-side alerts (from honeypots, rate-limit triggers, or repeated validation failures) prompt operators to engage feature flags, rotate keys, or adjust guardrails. The transparency ledger plus server logs provide the forensic trail for recovery.

9. Deployment & Data Boundaries
-------------------------------
- **Client:** WebExtension codebase (Chrome, Firefox parity) built from the `extension/` workspace.
- **Server:** Vercel-hosted API, managed via environment variables and CI/CD. No persistent database is required for the MVP; session state is ephemerally captured in the extension.
- **Data Handling:** Only policy excerpts and deterministic metadata leave the browser. No user accounts, telemetry, or persistent identifiers exist. Claude receives anonymized prompts and responds with structured JSON; all reasoning is shown to the user without alteration.
- **Future Iterations:** Plans include expanding guardrail catalogs, adding enterprise-tunable thresholds, and supporting additional vertical-specific heuristics while preserving the same transparency-first contract.
